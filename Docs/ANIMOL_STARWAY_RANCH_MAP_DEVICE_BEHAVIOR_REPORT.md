# 별길 목장 장치 로직 규칙서 — LLM 맵 제작용

2026-10-28 현재 활성 프로젝트의 **시나리오 퍼즐 판정**을 기준으로 작성했다. 이 문서는 장치를 조합해 새 별길 목장 맵을 설계할 때 필요한 입력 조건, 상태 변화, 연쇄, 배치 제약을 설명한다. 그림·클립 목록은 퍼즐 규칙이 아니다. 최신 수문은 V13 R3, 양은 V13 R2, 병아리의 판정은 V12, 귀환 표현은 V13 R4다.

> 적용 범위: 새 맵은 `themeId = "starway"`인 `PuzzleScenario`를 `PuzzleMap.scenario`에 연결해 `PuzzleDeviceSession`으로 실행한다. 현재 기본 플레이 씬의 `StarGarden.asset`은 시나리오가 없는 고전 `DeviceCell` 맵이므로 아래 V13 장치 규칙을 시험할 기준 맵이 아니다.

## 1. 모든 장치가 공유하는 보드 규칙

- 좌표는 `(x,y)` 정수 격자다. `+x=동`, `+y=북`; 입력은 북 `(0,1)`, 동 `(1,0)`, 남 `(0,-1)`, 서 `(-1,0)`의 **한 칸**만 허용한다. 대각 입력은 성공 행동이 아니다.
- 통행 가능한 칸은 맵 안에 `blocked=false`인 지형이 있고, 장식의 **게임 점유**가 없는 칸이다. 그림이 높거나 넓다는 이유로 추가 점유를 추론하지 않는다. 벽·차단 장치·양·소비 전 키 큰 풀·수문의 현재 물칸 등도 각 판정에서 통행을 막는다.
- `PrototypeDevice`는 고유 `id`, 공식 `role`, `variant`, 현재 셀을 정하는 `position`, `direction`을 갖는다. 같은 장치의 누름판·본체 등을 연결할 때만 같은 `group`을 쓴다. 양·수문·키 큰 풀은 `PrototypeRole` 번호를 새로 만들지 않고 `ranchV13Art`의 `family`와 고유 `instanceId`로 저장한다.
- 입력은 **변경 전 상태의 복사본**에서 판정한다. 거절되면 이동·장치 상태·코스트·장치 턴이 모두 0 변화다. 성공한 직접 입력 하나는 `Cost +1`, `EndTurn` 한 번이다. 자동 이동의 칸 수와 애니메이션 프레임 수는 추가 코스트가 아니다.
- `costLimit=0`은 무제한이다. 한도 값이 양수이면 성공 행동 뒤 먼저 승리 조건을 검사하고, 아직 승리하지 못한 상태에서 `Cost >= costLimit`이면 실패한다. 승리 행동 자체가 한도에 도달하는 것은 허용된다.
- 승리는 **플레이어가 출구에 있고**, 수집한 방울 수가 `targetBubbles` 이상이며, `scenario.goals`가 전부 참일 때만 확정한다. 목표 종류는 `Active`, `Removed`, `Position`, `DiceTop`, `Visited`다. `Visited`는 좌표 방문이고 나머지는 `PrototypeDevice.id`를 참조한다. 양의 소멸, 풀 소비, 수문 물 위상을 직접 참조하는 목표 종류는 현재 없다. 이런 상태를 필수로 만들려면 길 구조로 강제하거나 목표 기능을 별도로 구현해야 한다.
- 방울은 시작 칸 또는 이동으로 도착한 칸에서 수집된다. 별 홈 보상으로 나타나는 방울은 홈이 활성화된 뒤에 보이고, 플레이어가 그 칸에 도착해야 수집된다. 병아리 귀환이나 양의 풀 소비 자체가 방울·출구 보상을 자동 발생시키지 않는다.
- 성공 행동은 Undo에 **행동 전 보드 전체**를 쌓는다. 플레이어 위치, 일반 장치 상태, 양의 위치·존재, 먹힌 풀, 수문 물 위상, 병아리 추종·귀환, 방울과 코스트가 같은 단위로 되돌아간다. Reset은 맵의 초기 배치로 돌아간다. 클립 종료 시점에 게임 상태를 바꾸지 않는다.

### 한 입력의 우선순위

1. 인접 바람개비 본체를 향한 입력이면 플레이어는 움직이지 않고 바람 단계만 순환한다.
2. 그렇지 않고 인접 칸에 별양이 있으면 **별양 전용 밀기**를 먼저 판정한다.
3. 그렇지 않고 플레이어가 수문 쌍의 마른 칸에 있고 짝 물칸으로 입력했다면 **수문 교환**을 일반 물 진입 거절보다 먼저 판정한다.
4. 위 조건에 해당하지 않으면 일반 걷기·밀기·일방향 문·차단을 판정한다. 성공한 플레이어 이동 뒤 병아리 추종/둥지, 연결 상태, 바람 경로, 자동 이동을 처리한다.
5. 성공한 입력의 끝에 비용 한 번과 장치 턴 한 번을 적용한다. 장치 턴에는 바람에 놓인 물체·양의 이동 등이 포함될 수 있다. 예컨대 양을 직접 한 칸 민 입력에서 이어진 바람 운반도 같은 한 수다.

플레이어 자동 이동의 현재 우선순위는 **포털 → 일방향 문 출구 → 도약대 → 제동판 → 무빙워크 → 바람 → 얼음 → 강제 이동 중 반사판**이다. 앞 단계가 경로를 끝내면 뒤 단계를 그 칸에서 적용하지 않는다. 순환은 반복 상태 감지와 보드 크기 기반 한도로 끊는다. 아래에 없는 장치 간 경합 순서를 새 규칙으로 가정하지 않는다.

## 2. 별길 목장 장치별 판정

### 01 별돌과 별 홈 (`StarSocket`)

| 요소 | 규칙 |
|---|---|
| 배치 | 이동 돌과 고정 홈 모두 `role=StarSocket`. 홈은 `variant="socket"`; `number`가 문양 번호다. 서로 다른 인스턴스 ID를 쓴다. |
| 돌 밀기 | 플레이어가 돌을 향해 입력하고 돌의 다음 칸이 비어 있으면 돌을 한 칸 밀고 플레이어가 돌의 전 칸으로 간다. 일반 밀기와 동일한 입력 1회 비용이다. 바람에 실린 돌도 실제 경로에서 홈에 들어갈 수 있다. |
| 홈 일치 | 돌의 `number`와 홈의 `number`가 같으면 돌은 제거되고 홈은 `active=true`가 되어 그 칸을 통과 가능한 별 바닥으로 취급한다. |
| 홈 불일치 | 다른 문양의 홈으로 밀려는 입력은 돌·플레이어·홈을 바꾸지 않으며 코스트·턴 0이다. 빈 홈에는 플레이어가 직접 들어갈 수 없다. |
| 선택적 보상 | `socketReward=None`이면 홈만 활성화한다. `RevealBubble`이면 지정한 통행 가능 칸에 숨겨 둔 방울이 보인다. `RevealBridge`는 옛 다리 맵과의 호환 규칙이며 신규 별길 목장 목록의 기본 선택이 아니다. |

### 07 무빙워크, 18 반사판, 19 제동판

| 장치 | 규칙과 조합 |
|---|---|
| 무빙워크 (`Conveyor`) | 플레이어가 올라서면 저장된 `direction`으로 한 칸씩 강제 이동한다. 다음 칸이 막히거나 다른 종료 규칙을 만나면 멈춘다. 움직인 칸마다 추가 입력 비용을 내지 않는다. |
| 반사판 (`Bounce`) | 플레이어가 **강제 이동 중** 반사판에 오면 `orientation`에 따라 진행 방향을 직각으로 바꾼다. 맞지 않는 입사 방향이면 그 지점에서 자동 이동이 끝난다. 바람 경로 자체도 유효한 코너에서 직각으로 꺾이며, 코너 한 칸이 범위 한 칸을 소비한다. |
| 제동판 (`Brake`) | 무빙워크 등으로 `forced`인 플레이어 또는 활성 바람 위 플레이어가 제동판에 도착하면 그 칸에서 자동 이동을 끝낸다. 제동판 자체는 추가 코스트를 내지 않는다. |

반사판의 현재 `orientation` 매핑은 `0=nw: 북→동/서→남`, `1=ne: 동→남/북→서`, `2=se: 동→북/남→서`, `3=sw: 서→북/남→동`이다. 맵을 생성할 때 그림 이름만 보고 회전 방향을 추측하지 말고 이 입력→출력 쌍으로 검증한다.

### 09 일방향 문 (`OneWayGate`, V12 판정·그림)

- 문은 **한 칸**을 점유하고 `direction`이 허용 통과 방향이다. 예를 들어 동향 문은 서쪽 이웃에서 동쪽으로 들어가야 한다.
- 진입 전에 문 다음의 출구 칸 `(문 셀 + direction)`이 비어 있는지 검사한다. 허용되면 문 셀을 거쳐 같은 행동 안에서 출구까지 이동한다. 두 칸 이동이어도 코스트는 1이다.
- 옆·뒤에서의 진입, 문 위에서 허용 방향이 아닌 탈출, 막힌 출구는 거절한다. 거절된 입력에는 0 비용이다. 밀리는 물체가 문을 통과할 때도 방향 검사를 거친다.
- V13 그림 키를 이유로 새 문 판정을 만들지 않는다. 현재 별길 목장 문은 요청대로 V12 표현을 쓴다.

### 20 바람개비와 바람 (`Wind`)

- `variant="blower"`가 고정 본체다. 플레이어가 본체를 향해 입력하면 플레이어 제자리에서 `phase 0→1→2→3→0`으로 변한다. 각각 영향 최대 범위는 **0/3/6/9칸**이다. 본체를 실제로 밀거나 바람 길을 별도 타일로 배치하지 않는다. 초기 세기는 `orientation`에서 시작한다.
- 바람은 본체의 `direction` 다음 칸부터 실제 영향을 받는 셀을 추적한다. 벽·지형 없음·금속 상자·병아리 같은 차단체의 **직전**에서 멈추며 그 뒤에는 바람이 없다. 반사판이 바람을 꺾으면 남은 범위만 이어 간다. 같은 셀을 다시 방문하는 순환은 멈춘다. 오프 상태에서는 이전 화살표나 끝 표시가 남지 않는다.
- 활성 바람 위에 진입한 플레이어는 실제 영향 경로의 끝 또는 장애물 직전까지 자동 이동할 수 있다. 제동판이 있으면 그 칸에 멈춘다. 나무 상자는 바람 경로에서 운반되며 금속 상자는 움직이지 않고 바람을 차단한다. 별돌도 바람으로 이동해 맞는 홈에 앉을 수 있다.
- 별양은 별도의 R2 바람 판정으로 실제 유효 셀을 따라 마지막 이동 가능 칸까지 가거나 첫 키 큰 풀에서 소멸한다. **현재 V12 병아리는 바람 운반 대상이 아니며 바람을 막는 차단체다.** 과거 V13 기획의 병아리 운반을 현 규칙으로 가정하지 않는다.
- 옛 `variant="field"`는 자기 칸에서만 작용하는 고정 바람의 호환 데이터다. 새 테마 장치 목록에서는 숨겨져 있고 범위형 바람개비의 3/6/9 경로를 대신하지 않는다.

### 24 병아리와 둥지 (`Chick`, V12 판정 + R4 귀환 표현)

- 병아리는 `PrototypeDevice` 한 개이며, 시작 `position`, 둥지 좌표 `target`, 추종 지연 `number`를 가진다. `target=(0,0)`은 **둥지 미지정**이다. 둥지는 독립 장치 ID나 `ranchV13Art` 항목이 아니라 병아리의 `target`에 연결된 목표 칸이다.
- 귀환 전 병아리는 **차단체**다. 플레이어와 상자가 그 칸을 통과할 수 없고, 병아리가 일반 누름판 위에 서면 점유로 판정된다. 병아리의 몸을 플레이어가 일반 상자처럼 밀지 않는다.
- 플레이어가 실제로 이동할 때마다 병아리는 플레이어가 떠난 칸을 `trail`에 기록한다. 기록 길이가 `clamp(number,1,8)`을 넘으면 가장 오래된 칸으로 **한 칸** 따라가려 한다. 그 칸이 인접하지 않거나 비어 있지 않으면 그 추종 시도는 건너뛴다. 벽을 통과하는 직선 이동이나 최단 경로 탐색을 하지 않는다. 자동 이동의 각 실제 플레이어 이동도 이 흐름에 들어간다.
- 각 플레이어 이동의 추종 처리 시작에 병아리가 지정 둥지의 **빈 인접 칸**에 있으면 먼저 둥지로 한 칸 들어갈 수 있다. 이미 둥지 칸에 도착했다면 귀환 상태가 된다. 병아리의 `active=true`, 추종 기록 삭제, 이후 추종 중지가 한 번 확정된다. 단순히 플레이어나 둥지가 근처에 있다는 이유만으로 멀리서 둥지로 순간 이동하지 않는다.
- 귀환 성공 후 실제 접근 방향으로 R4 폴짝 도착·앉기 그림을 재생하고 앉은 상태를 유지한다. 이 그림이 귀환 판정이나 추가 비용을 발생시키지 않는다. 현재 논리 상태에서 `active` 병아리도 `Solid` 판정이므로 둥지 칸의 점유가 자동으로 사라진다고 가정하지 않는다.

### V13 R2 별양과 키 큰 풀 (`ranchV13Art`)

- 양은 `family="sheep"`, 풀은 `family="tall_grass"`로 각각 한 칸에 배치한다. 풀은 소비 전 통행을 막고, 소비 뒤 바닥이 된다.
- 플레이어 바로 앞 양을 향해 입력하면 양이 입력 방향으로 **정확히 한 칸** 이동하고 플레이어는 **제자리**다. 목적지가 벽·수문의 물칸·다른 양·플레이어·차단체라면 실패하고 0 비용이다. 양 여러 마리를 연쇄로 밀지 않는다.
- 양의 목적지가 키 큰 풀이면 **풀 한 칸과 양이 동시에 제거**된다. 먹은 뒤 양이 남거나 다음 풀을 계속 먹지 않는다. 풀·양 제거는 논리적으로 즉시 확정하고 먹기 그림은 후속 표현이다.
- 유효 바람 위의 양은 실제 바람 영향 셀을 따라 끝/장애물 직전까지 운반된다. 도중 **첫 풀**을 만나면 그 칸에서 풀과 양이 사라진다. 직접 밀기 뒤 같은 성공 행동에서 바람이 이어져도 입력 코스트는 1뿐이다. Undo·Reset은 양과 풀을 함께 복원한다.

### V13 R3 가로·세로 수문 (`ranchV13Art`)

- 한 수문 인스턴스는 서로 상하 또는 좌우로 **정확히 한 칸 이웃한** `A=position`, `B=pondB`를 점유한다. 가로는 2×1, 세로는 1×2이고 제3의 레버·수로 칸은 없다. `hasPondB=true`이면 명시한 B를 사용하고, 오래된 배치는 `B=A+direction`을 쓴다. 저장 필드 `rightState`의 뜻은 **A가 젖었는가(`wetA`)**이지 “오른쪽이 젖었는가”가 아니다. A/B 순서를 좌표 정렬로 바꾸지 않는다.
- 항상 한 칸만 물이고 다른 한 칸은 마른 구덩이다. 플레이어가 **그 쌍의 마른 칸에 서서 짝의 물칸 방향으로** 입력할 때만 교환한다. 주변 바닥에서 물칸으로 들어가는 입력이나 같은 쌍이 아닌 이동은 이 예외에 해당하지 않는다.
- 목적지 점유와 출발 칸에 남을 다른 침수 객체 정책을 먼저 검사한다. 유효하면 `출발 마른 칸→젖음`, `도착 물칸→마름`, `플레이어→도착`을 원자적으로 확정한다. 플레이어 경로는 `[행동 전 Dry, 행동 전 Wet]`, 물 경로는 그 반대 `[행동 전 Wet, 행동 전 Dry]`다. 출발 플레이어 자신은 침수 장애물로 세지 않는다.
- 실패하면 물 위상·플레이어·코스트·물 흐름 연출 모두 바뀌지 않는다. 성공은 코스트/장치 턴 각 1이고, 그 뒤의 자동 이동에 추가 비용은 없다. Undo·Reset은 두 셀의 물 위상과 플레이어를 같은 단위로 복원한다.
- 수평 예: `A=(2,2) 마름`, `B=(3,2) 물`에서 동 입력 → 플레이어 `(3,2)`, 물 `(2,2)`. 다시 서 입력하면 원래 위상으로 돌아간다. 세로에서도 북·남만 바꾸어 같은 규칙을 적용한다.

### 고정 물칸·상자·장식

- `scenario.water`는 **고정 물 셀 목록**이다. 수문 A/B와 중복 배치하지 않는다. 현재 시나리오 호스트에서 `water` 목록만 추가하고 기초 지형을 통행 가능하게 두면 일반 통행과 양 이동까지 자동 차단된다고 보장할 수 없다. 고정 물을 퍼즐 장애물로 쓸 때는 바닥·진입 판정을 실제로 시뮬레이션하고, 의도한 차단 지형을 함께 설계한다. 수문의 젖은 칸은 별도 `RanchWet` 판정으로 차단된다.
- `WoodCrate=102`, `MetalCrate=103`은 일반 밀기에서 한 칸 전진하고 플레이어가 상자의 전 칸으로 들어간다. 나무 상자는 활성 바람 운반 대상이다. 금속 상자는 바람에 밀리지 않고 그 지점 뒤의 바람을 막는다. 둘 다 병아리·다른 차단체로 막힌 칸에 밀 수 없다.
- 연결 장식 V02의 26종과 고정 풍차 장식은 **장치 입력이나 턴을 발생시키지 않는다.** `DecorationCell`의 게임 점유 크기는 그림 캔버스 크기와 별도이며, 점유 칸은 이동을 막는다. 특히 헛간 그림은 3×2이지만 현재 게임 점유는 3×1이다. 장식 바람개비를 기능성 20번 바람개비로 취급하지 않는다.
- 옛 02 누름판·덩굴 다리(`VineBridge`)는 저장된 맵에서 여전히 작동한다. 플레이어 또는 고체 객체의 누름판 점유가 연결 그룹을 켜고, 다리 위가 점유 중이면 수축을 보류할 수 있다. **신규 별길 목장 테마 장치 목록에서는 제외**되어 있으므로 새 맵의 기본 장치로 다시 도입하지 않는다.

### 최소 행동 예시

| 행동 전 상태 | 입력 | 행동 후 상태 |
|---|---|---|
| 플레이어 `(1,2)`, 양 `(2,2)`, 풀 `(3,2)` | 동 | 플레이어 `(1,2)` 유지, 양·풀 제거, 코스트 1 |

| 플레이어 `(2,2)`, 수문 A=`(2,2)` 마름·B=`(3,2)` 물 | 동 | 플레이어 `(3,2)`, A 물·B 마름, 코스트 1 |
| 플레이어가 동향 문 바로 서쪽, 문 동쪽 출구에 벽 | 동 | 플레이어·문 상태 유지, 코스트 0 |

## 3. LLM이 생성할 맵 데이터 계약

다음은 **설계용 중간 표현**이다. Unity `.asset`을 그대로 대체하는 JSON 형식이 아니다. 각 항목을 실제 `PuzzleMap`과 `PuzzleScenario`에 대응시키고, `PuzzleMap.theme`에는 현재 별길 목장 테마 에셋을, 각 기존 장치에는 해당 테마의 `visualPrefab`을 연결한다. 정식 에셋/프리팹 참조는 프로젝트 제작기로 연결한다.

```json
{
  "themeId": "starway",
  "size": [9, 7],
  "walkableCells": [[1, 2], [2, 2], [3, 2], [4, 2]],
  "start": [1, 2],
  "exit": [4, 2],
  "bubbles": [[4, 2]],
  "targetBubbles": 1,
  "costLimit": 3,
  "devices": [
    {"id": "stone_1", "role": 1, "variant": "", "position": [2, 2], "direction": [1, 0], "number": 1},
    {"id": "socket_1", "role": 1, "variant": "socket", "position": [3, 2], "direction": [1, 0], "number": 1}
  ],
  "ranchV13Art": [],
  "water": [],
  "goals": [{"deviceId": "socket_1", "kind": "Active"}]
}
```

이 작은 예시의 예상 경로는 `동, 동, 동`이다. 첫 동 입력에서 돌이 홈에 앉고 플레이어는 `(2,2)`가 된다. 둘째 동 입력에서 활성 홈으로 들어가고, 셋째 동 입력에서 방울·출구·`Active` 목표를 동시에 만족한다. 세 번째 성공 입력에서 코스트 한도에 닿아도 승리가 먼저 판정된다.

새 맵마다 아래 순서로 생성·검증한다.

1. 시작·출구·방울과 모든 이동 가능 경로에 실제 지형을 놓는다. 시작/출구는 맵 안의 통행 가능 칸이어야 하고, 보이는 방울과 홈 보상 방울을 합쳐 `targetBubbles`를 달성할 수 있어야 한다.
2. 모든 `PrototypeDevice.id`와 모든 V13 `instanceId`를 중복 없이 부여한다. 방향은 사방 한 칸 벡터로 저장한다. 누름판 연결이나 별 홈 보상은 대상 ID·그룹을 명시한다. 템플릿을 복제하면 병아리 `target`은 0으로 초기화되므로 다시 지정한다.
3. V13 양·풀은 각각 1칸, 수문은 정확히 인접한 2칸에 놓는다. V13 점유 셀끼리 또는 `PrototypeDevice.position`과 겹치지 않게 한다. 수문 두 칸에 기초 통행 가능 지형을 놓고, 시작은 물칸에 두지 않는다. 양·풀 위에도 시작하지 않는다.
4. 병아리 둥지는 독립 객체로 추가하지 말고 해당 병아리 `target`을 통행 가능한 빈 칸으로 지정한다. 병아리 시작 칸은 둥지·플레이어 시작 칸과 분리한다. 둥지로 가는 추종 경로의 **실제 인접 칸**과 귀환 뒤 점유를 시뮬레이션한다.
5. 바람은 본체의 방향·초기 `orientation`(0/1/2/3)과 실제 차단체로 영향 셀을 계산한다. 반사판·제동판을 포함한 자동 경로와 상자/양/병아리의 서로 다른 취급을 추적한다. 의도한 길이 3/6/9 그림만 보고 영향 범위를 추정하지 않는다.
6. 모든 입력을 초기 상태에서 순서대로 재생한다. 각 단계의 플레이어·양·병아리·풀·수문·바람 상태, 코스트와 방울을 기록한다. 정답 경로뿐 아니라 막힌 입력 0 비용, 문 출구 차단, 양 앞 장애물, 물 교환 실패, Undo·Reset도 검사한다.

## 4. 새 맵에서 피해야 할 미확정 조합과 현행 주의점

- 병아리 등 다른 객체를 수문 출발 칸에 남겨 침수시키는 상황은 `floodPolicyHolds`로 보류한다. 수문 교환 직후 병아리의 재추종 방식, 포털·도약·배를 통한 병아리의 새 이동 경로는 임의로 보충하지 않는다.
- 바람·무빙워크·제동판·반사판이 동시에 여러 객체에 영향을 주는 복잡한 경합은 **현재 코드 순서로 시뮬레이션**해야 한다. 새 우선순위나 연쇄 밀기를 설정하지 않는다.
- 기존 `starway` 프로토타입에는 옛 덩굴 다리가 남아 있지만, 새 제작기 목록에는 없다. 이를 새 테마의 필수 장치로 복원하지 않는다.
- `scenario.water`의 시각만 보고 차단을 가정하지 않는다. 특히 통행 가능한 지형 위에 고정 물을 놓은 맵, 고정 물과 양·바람의 조합은 별도 검증이 필요하다.
- 양 소멸과 수문 위상은 현재 `PrototypeGoal`로 직접 지정할 수 없다. 해당 동작이 필요하지만 우회 경로가 있는 맵을 “목표 검증 완료”로 표시하지 않는다.
