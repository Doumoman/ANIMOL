ANIMOL의 기존 탑뷰 퍼즐 프로젝트에 공통·별길 목장 장치 8종 아트를 실제 적용하라.
입력: mcp_inbox 또는 프로젝트 루트의 ANIMOL_DEVICE8_V01.zip.
이 팩은 ANIMOL_REFERENCE_SPRITES_V04에 추가하는 장치 팩이다.
기본 배경·UI·토끼·분홍 비눗방울의 V04 적용을 유지하고 아래 8종을 연결하라.
계획만 작성하지 말고 실제 자산·프리팹·씬과 확인 결과를 남겨라.

0. 먼저 확인할 자료
- 프로젝트 AGENTS.md, ProjectVersion.txt, Packages/manifest.json.
- ZIP의 README_KO.md, manifest.json, unity_import_manifest.json, DEVICE_EVENT_BINDINGS.csv.
- source/ADDED_DECISIONS_KO.md와 QA_REPORT.json.
- JSON은 프로그램으로 전체 파싱하되 출력은 필요한 요약으로 제한하라.
- 현재 플레이 씬, 장치 데이터, 장치 ID/enum, 맵 로더, 입력·이동·턴 처리의 실제 파일을 찾아라.
- 코스트·자동 연쇄·충돌·누름판 점유·추종 경로·출구의 소유자를 확인하라.
- 문서상의 ID를 프로젝트 enum 숫자로 무조건 캐스팅하지 말고 실제 매핑을 기록하라.

1. 작업 범위와 규칙
- 공통: 07 무빙워크, 09 단방향 문, 18 튕김 모서리, 19 제동판.
- 별길 목장: 01 별돌 끼움홈, 02 누름판·덩굴 다리, 20 바람 통로, 24 따라오는 병아리.
- 기존 유효 행동 코스트 1, 무효 입력 코스트 0·장치 턴 0을 유지하라.
- 한 행동 안 굴림·무빙워크·바람 등 자동 연쇄에 추가 코스트를 만들지 말라.
- 장치의 게임 상태는 유효 행동 사건에서 처리하며 실시간 애니메이션 반복으로 턴을 진행하지 말라.
- 방울 3개 후 출구 성공, 기존 이동 거리·정지·실패·리셋 규칙을 유지하라.
- 레거시 러너·점프·스태미나 코드를 이번 퍼즐 규칙에 섞지 말라.
- 해당 장치 로직이 없으면 임포트·표현 프리팹·QA 씬은 완성하고 미연결 항목을 보고하라.
- 미연결을 숨기기 위해 임의의 새 게임 규칙을 구현하지 말라.

2. 파일 배치와 임포트
- 프로젝트의 기존 Sprites 정리 규칙을 우선 확인하라.
- 기본 대상은 Assets/ANIMOL/Sprites/Obstacles/common 및 starway_pasture이다.
- 기존에 같은 역할의 Sprites 루트가 있으면 그 경로를 재사용하고 두 번째 루트를 만들지 말라.
- ZIP sprites/obstacles 아래 장치별 폴더를 대응 경로로 가져오고 원본→프로젝트 경로표를 남겨라.
- static PNG와 개별 애니메이션 프레임을 사용하라. 시트와 개별 프레임을 중복 연결하지 말라.
- preview/reference/source/생성 원화/GIF/합성 검수 이미지를 런타임 스프라이트로 임포트하지 말라.
- 신규 게임 PNG는 Sweetie16의 15색, 알파 0/255다. 재채색·디더링·자동 리사이즈를 하지 말라.
- Texture Type Sprite, Full Rect, Alpha Source Input, Alpha Is Transparency=true.
- Filter Point, Wrap Clamp, Mip Maps=false, NPOT 리사이즈 없음.
- 우선 무압축으로 검수하고 Max Size나 플랫폼 Override가 크기를 줄이지 않게 하라.
- Atlas를 사용하면 회전·타이트 패킹을 끄고 패딩 4px로 번짐을 확인하라.
- 기존 셰이더·렌더 파이프라인에 맞는 알파 블렌딩을 사용하라.
- 기존 AssetPostprocessor가 32 PPU·압축·피벗을 덮어쓰는지 확인하고 이번 경로에 한정해 수정하라.
- 임포트 manifest의 pixelsPerCell은 80이다. 기존 셀의 월드 폭이 s이면 PPU=80/s다.
- 일반 PNG 96×96, 덩굴 다리 128×128, 병아리 64×64다. 논리 셀은 80px다.
- 캔버스 크기를 셀 간격으로 사용하거나 전역 Grid·물리 크기를 바꾸지 말라.
- 피벗은 PNG 왼쪽 위 기준이다. Unity 값은 (pivotX/width,1-pivotY/height)다.
- 일반 피벗 [48,48], 다리 [64,64], 병아리 [32,54]를 프레임마다 동일하게 사용하라.
- 자동 Trim·프레임별 중심 재계산을 금지하라.
- Renderer.bounds나 Sprite 알파로 Collider·점유 칸을 다시 만들지 말라.
- 기존 .meta/GUID와 참조를 보존하거나 모든 참조를 확인해 갱신하라.

3. 공통 애니메이션 연결
- JSON의 프레임별 durationMilliseconds와 누적 startMilliseconds를 사용하라.
- 동일 fps로 임의 환산하지 말고 클립 종료 시각까지 보장하라.
- 기존 애니메이션/표현 구조를 재사용하고 중복 코스트·턴·장치 매니저를 만들지 말라.
- 물리 Root와 Collider는 기존 로직이 담당하고 시각 Renderer만 변경하라.
- 논리 결과는 기존 커밋 시점에서 확정한다. AnimationEvent로 다시 이동·수집·점유를 커밋하지 말라.
- 반복 클립은 기존 일시정지 정책에 맞춰 정지하고 리셋 시 적절한 초기 상태를 복원하라.
- 시각적 시작 위상은 장치 ID 해시나 독립 시각 RNG를 쓰고 게임플레이 RNG를 소비하지 말라.
- 기존 효과음이 있다면 실제 작동 사건당 한 번만 연출과 동기화하라.
- 모바일 햅틱은 기존 서비스와 사용자 설정을 재사용하라. idle에는 붙이지 말라.
- 일반 장치 접촉마다 화면 흔들림·줌·히트 스톱을 추가하지 말라.

4. 07 무빙워크
- e/s/w/n은 화면 기준 오른쪽/아래/왼쪽/위다. 월드 좌표와 대응을 확인하라.
- 방향별 idle PNG와 run 클립을 실제 방향 데이터에 연결하라.
- 벨트 반복은 시각 표시다. 프레임 변화가 대상을 밀거나 비용을 차감해서는 안 된다.
- 운반 끝·막힌 앞칸에서의 정지와 자동 연쇄 종료는 기존 로직을 유지하라.

5. 09 단방향 문
- 닫힘 closed, 통과 시작 open, 실제 통과 완료 close를 기존 사건에 연결하라.
- 문의 기둥은 고정하고 문짝만 움직이는 완성 프레임을 사용하라.
- 반대 방향 입력에는 기존 거부 사건에서 blocked를 한 번 재생할 수 있다.
- 거부 반응 때문에 비용이나 장치 턴을 진행하지 말라.
- open 클립이 끝나면 열린 상태를 유지하라. 실제 통과 완료 전에 시간만으로 닫지 말라.
- 일시정지·리셋·취소 시 논리 통과 상태와 문 시각 상태가 일치하게 복원하라.

6. 18 튕김 모서리
- NW/NE/SE/SW는 단단한 벽이 붙은 모서리다. 열린 쪽은 반대 대각 방향이다.
- 기존 반사 규칙과 시각 방향을 대조하라: NW N→E/W→S, NE E→S/N→W,
  SE E→N/S→W, SW W→N/S→E. 이는 이동 벡터 기준이다.
- 실제 프로젝트 enum이 다르면 뷰 매핑을 고치고 게임 규칙을 바꾸지 말라.
- 안쪽 투명한 홈을 채우거나 정사각형 SpriteMask/Collider로 막지 말라.
- 기존 강제 이동의 방향이 바뀌는 사건에서 impact를 한 번 재생하라.
- 다음 칸 막힘·정지·추가 코스트 없음은 기존 자동 이동 로직을 유지하라.

7. 19 제동판
- horizontal/vertical은 정지선 외형 두 가지다. 새 방향 제한 규칙이 아니다.
- 기존 강제 이동 종료 사건에서 brake 클립을 한 번 재생하라.
- 별도 반발·밀림·추가 행동·추가 비용을 만들지 말라.
- 이동 잔상이나 운반 시각 효과가 있다면 제동판 도착에서 정리하라.

8. 01 별돌 끼움홈
- stone, socket_empty, socket_filled를 별도 역할에 매핑하라.
- 실제 유효 밀기에서 방향별 stone_push를 재생하고 Root 이동은 기존 코드가 담당하게 하라.
- 일치하는 별돌이 홈에 들어가 바닥이 되는 기존 커밋 사건에서 socket_insert를 재생하라.
- 완료 후 socket_filled를 유지하고 돌을 다시 밀 수 있는 중복 Renderer/Collider를 남기지 말라.
- 별돌의 위쪽 꼭짓점은 고정한다. 이동 방향 때문에 별 전체를 90도 회전시키지 말라.
- 다른 문양을 만났을 때의 처리는 기획에서 미확정이다. 기존 구현을 유지하고 없으면 보고하라.

9. 02 누름판·덩굴 다리
- 점유 0→양수에서 plate_press, 양수→0에서 plate_release를 한 번만 호출하라.
- 여러 점유자가 있을 수 있으므로 마지막 점유자가 나가기 전에 시각적으로 해제하지 말라.
- 일반 누름판을 누르지 않는 병아리의 기존 제외 규칙을 유지하라.
- 연결된 다리의 기존 활성/비활성 사건에 bridge_extend/retract 방향별 클립을 연결하라.
- 완성 다리와 접힌 다리의 완료 상태를 유지하라. 실행 중 매 프레임 같은 클립을 재시작하지 말라.
- 다리의 128×128 전체 프레임을 80px 간격으로 겹쳐 배치하라. 잎을 셀 경계로 자르지 말라.
- 앞뒤 타일의 렌더 순서와 Tilemap Chunk Culling Bounds를 실제 흔들림 외곽까지 확인하라.
- 연결 덩굴과 끝 장식은 시각 부품이다. 별도 통행 가능 칸이나 Collider로 추가하지 말라.
- 점유 중 다리를 회수하는 예외는 미확정이다. 기존 구현을 유지하고 임의 낙사·구출 규칙을 만들지 말라.

10. 20 바람 통로
- 방향별 blower_run과 wind_flow, 필요 시 기존 밀림 사건의 wind_push를 연결하라.
- 완성된 blower_run에는 고정 몸체와 날개가 모두 들어 있다. housing을 중복 표시하지 말라.
- housing PNG는 별도 레이어 구성이 필요한 경우에만 사용하라.
- 날개·바람 반복은 시각 표시이며 유효 행동마다의 실제 한 칸 밀림은 기존 로직에서 처리한다.
- 금속 상자의 면역·뒤쪽 바람 차단과 막힌 다음 칸의 정지를 기존 규칙대로 유지하라.
- 바람줄은 실제 영향 셀에만 표시하라. 금속 뒤·벽 뒤·범위 밖까지 그리지 말라.
- 기존 나무 상자는 V04 자산을 사용하고, 이 팩의 metal_crate는 기존 금속 상자 역할에만 매핑하라.

11. 24 따라오는 병아리
- 앞·뒤·좌·우 idle/walk를 실제 이동 방향과 정지 상태에 연결하라.
- SpriteRenderer 발 피벗을 유지하고 기존에 기록된 플레이어의 실제 경로를 따라가게 하라.
- 최종 위치로 직선 보간하여 벽을 관통하는 새 추종 방식을 만들지 말라.
- 유효 이동이 없으면 따라오기 행동을 만들지 말라. 병아리 자체 비용도 추가하지 말라.
- 병아리는 길을 막지 않으며 일반 누름판을 누르지 않는다. 자동 생성 Collider로 이 규칙을 깨지 말라.
- 포털·도약·배·둥지 판정은 미확정이므로 기존 코드가 제공하는 경로와 판정만 사용하라.
