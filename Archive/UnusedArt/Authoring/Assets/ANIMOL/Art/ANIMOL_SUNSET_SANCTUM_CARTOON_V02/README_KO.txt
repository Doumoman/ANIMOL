ANIMOL 낙일 성소 V02

낙일 성소의 지형·하부 마감·다리·돔/하늘·장식과 공통4종/성소5종 장치 1024개 전체를 새 원화로 다시 제작한 V02 최종 교체본이다. 둥근 표현을 직선과 꺾임이 뚜렷한 각진 형태로 바꿨다. 포털/도약 원판/렌즈는 다각형 하우징, U자석은 잘린 모서리, 돔은 면이 나뉜 다각 지붕, 아치는 뾰족하거나 단차진 사다리꼴, 구름은 길고 불규칙한 다각 리본으로 재설계했다. 볼트·랜턴 고리·천구의·두루마리 끝도 같은 원칙을 따른다. 굵고 각진 남색 윤곽선과 넓은 기본색+그림자 셀 음영을 사용하며 옛 픽셀 아트/16색/80PPU 규칙은 적용하지 않는다.
V01 이미지를 필터/양자화/외곽선 효과로 각지게 만드는 방식은 허용하지 않는다. 새 imagegen native 원화에서 모든 타일·별·화살표·FX·최신 endpoint 별칭까지 조립한다. 같은 1024개 파일 경로와 106개 클립 키, 방향·점유 계약·동작 규칙을 유지한다. PNG 인코딩만 달라진 것은 전면 수정으로 세지 않는다. 대응 파일의 실제 decoded RGBA가 모두 바뀌었는지 별도로 검사하고, 정말 완전 투명한 예외가 있다면 경로와 사유를 명시한다. V01 기준에는 완전 투명한 파일이 없다.
표시 이름은 스토리 전 낙일 성소, 실제 스토리 완료 플래그 이후 천구 날조국이다. 실제 테마 key/저장/맵/매칭 ID를 이름 변경과 함께 바꾸는 작업이 아니다.

다운로드와 압축 해제
인게임 설치에는 01_CORE, 02_FLOOR, 03_BRIDGES 세 ZIP이 모두 필요하다. 세 파일을 동일한 상위 폴더에서 같은 위치로 압축 해제하여 내부 ANIMOL_SUNSET_SANCTUM_CARTOON_V02 폴더 하나로 합친다. 번호별 폴더를 따로 만들거나 패키지 폴더 안에 같은 이름의 패키지 폴더를 중첩하지 않는다. 합친 뒤 런타임 PNG1024개/클립106개가 모두 있어야 한다. 04_SOURCES는 새 원화와 제작 구성요소를 편집·재제작할 때만 추가하는 선택 다운로드이며 인게임 설치에 필수는 아니다.
세 인게임 ZIP만 합친 폴더는 패키지 폴더에서 python QA/verify_sanctum_package.py --package . --report <검수JSON경로> --runtime-only로 검사한다(Python/Pillow 필요). 이 모드도 런타임 PNG/카탈로그/임포터/별칭/지형/배경 및 포함된 검토 씬 layout 검사를 수행하고, 선택 원본의 존재·바이트 SHA 검사를 생략했다고 보고한다. 제작 원본까지 합친 전체 검수는 같은 명령에서 --runtime-only를 빼고 실행한다. 외부 제작 export가 없는 배포본은 패키지 내 그룹 manifest와 대조했다고 기록하며, 옛 픽셀 baseline 원본이 없으면 그 비교는 NOT_AVAILABLE로 남긴다. 두 검수 모두 Unity 실제 실행을 대신하지 않는다.

제공 범위
런타임 PNG1024개(지형/하부784,배경/장식29,공통장치66,이동장치96,광학/유리49)와 클립106개로 구성된다. 정적 자산도 최신 카탈로그의 정확한 경로로 선택한다.
- 새 transparent PNG, 방향별 장치 상태와 전환 프레임, 최신 endpoint 별칭, 파일/원화 계약
- 최신 파일만 고르는 Unity 카탈로그·임포터·시각 코드와 경로 표시 연결용 코드
- 장면/경계/동작 검수 자료와 실제 프로젝트 적용 지시

적용
CLI_HANDOFF_KO.txt를 실제 Unity 프로젝트에서 작업할 CLI에게 전달한다. ANIMOL_SUNSET_SANCTUM_CARTOON_V02을 Assets 아래 새 패키지로 설치하고 실제 장치/보드/동작/Prefab 참조를 조사해 연결해야 한다. PNG만 복사하거나 옛 폴더를 통째 지우는 방식으로 끝내지 않는다. 기존 외부 GUID와 .meta를 무차별 치환하지 않고, 같은 새 패키지를 갱신할 때는 해당 .meta를 보존한다. 다른 테마나 공용 자산을 삭제하지 않는다.
V01이 이미 설치되어 있으면 V01 경로의 .meta를 V02에 복제하거나 외부 GUID를 일괄 치환하지 않는다. V02의 새 namespace ANIMOL.Art.SunsetSanctumV02와 최신 카탈로그를 생성한 다음 실제 성소 renderer/Prefab/풀/Animator 참조를 통제하여 V02로 옮긴다. 실제 theme/device ID·맵·세이브·방향 enum·점유·코스트는 바꾸지 않는다. V01은 전환 완료와 실제 참조0 확인 뒤에만 해당 미사용 범위를 정리한다. V01 원화 fallback은 허용하지 않는다.
최신 animation_catalog.json과 animation_catalog_sha256.txt를 확인하고 제공된 builder로 .asset/.anim을 생성한 뒤 각 시각 컴포넌트의 catalog와 expectedManifestSha256를 함께 연결한다. 광선 머티리얼도 제공된 별도 builder로 생성한다. 중복 행동 재생을 막는 sequence API와 풀 재사용 reset을 사용한다. 풀/Animator/초기화 코드가 옛 스프라이트로 덮어쓰는 경로도 점검해야 한다. 제공된 선택적 아트 검토 씬 builder는 별도 예시 씬만 만들며 실제 게임의 입력/맵/충돌/장치를 이식하지 않는다.

타일과 움직임
기본 논리 한 칸은256px/PPU256=world1이다. 보통320×320 이미지의 [32,32,256,256]이 지면 슬롯이며 여백이나 높이/회전 여유는 점유·Collider가 아니다. 다칸 원화와 별도 pivot은 개별 manifest를 따른다. 옛80PPU 자동 임포터와 fitToCell/autoScaleToBounds를 동시에 적용하면 크기와 경계가 어긋날 수 있다.
일방향 문은 실제 한 칸 점유, 출구는 검사만 한다. 반대/측면 입력은 닫힌 봉과 빨간X로 거절한다. 무빙워크의 구조/화살표/이동 축은 같고 제동판은 그 축을 가로지르는 정지선으로 보인다.
도약판은 표시 방향3칸 착지, 포털은 세계 방향과 걷기/미끄럼 상태를 보존한다. 걷기 포털은 짝 바깥 한 칸으로 나와 멈춘다. 광선 표시와 감지기/연결문은 같은 경로 결과를 사용한다. 유리는 빛만 통과시키고 몸체/바람을 막으며 기존 파괴 이벤트로 열린다. 금 간 프레임은 새 두 번 타격 규칙이 아니다. 자석은 금속만 자석 쪽으로 당긴다.
광원의 새 비대칭 원화를 한 칸에 충분히 채우면서 native iris 위치만 광선 축을 따라 이동한 시각 등록 예외20개가 있다. opticalAnchorPixel은 실제 iris의 시각 좌표이며 gameplay 원점이 아니다. logicalRayAnchorPixel=[160,160], 직교축 좌표와 칸 경계 출구는 그대로다. 변경 비교 보고서에 이 예외를 개별 기록한다.
2/3/4칸 연결 하부는 하나의 몸체처럼 이어지고, 긴 구간은 안정된 간격으로 변화해야 한다. 다리와 안쪽 구멍의 마감도 실제 이웃에 맞춰 배치한다. 별은 구름 뒤에서 거의 고정되고, 구름과 가까운 구조는 더 민감하게 움직인다. 깊이Z와 명시적 sorting을 함께 사용한다.

검수 상태와 미확정 규칙
실제 RGBA 변경과 불변 메타데이터/새 native 참조 비교에는 V02의 04_SOURCES를 함께 풀고 V01 원본 패키지도 준비해야 한다. python QA/compare_v01_angular_revision.py --baseline <V01원본패키지경로> --package <V02패키지경로> --report <변경검수JSON>으로 실행한다. 인게임 01~03 합본의 설치 검사에는 앞의 --runtime-only 명령을 사용한다. hash 변화는 각진 그림체의 증명이 아니므로 angular_required_qa_checklist.json의 원화·장치·건축·구름·최종 씬 육안 검수를 함께 완료해야 한다.
파일 기반 원화/프레임/경계 검수와 실제 Unity 게임 검증을 구분한다. 제공 예시 이미지는 새 아트와 선언된 경로를 조합한 오프라인 검수 화면이며 실제 게임 스크린샷이 아니다. 원본 Unity 프로젝트를 받지 못했으므로 Import/C#/Shader컴파일/NUnit/씬 바인딩/Play Mode/실제 레거시 참조0은 NOT_RUN이다.
도감은 도약판의 정확한 입력 시점·중간 칸 반응·막힌 착지 처리와 거울 직접 조작 입력을 확정하지 않았다. 실제 기존 구현을 확인해 연결하고 원화나 이펙트에서 새 규칙을 추측하지 않는다. QA의86개 실제 실행 시나리오는 프로젝트에서 근거를 남기며 검증해야 한다.
